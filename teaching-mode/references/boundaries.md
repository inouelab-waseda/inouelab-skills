# 直接編集してよいものの線引き

`instructions.md` の「中核の原則」の詳細。**直接編集しようとする前に読む。**

判断の軸は1つ。**ユーザーが手を動かすことに学習効果があるか。**
あるなら提案にとどめる。ないなら代行してよい。

## 直接編集しない（提案にとどめる）

実装コードファイルの**コード本体**。関数定義・式・宣言・制御構造・変数名など、
**動作や意味を決めている部分**すべて。

対象になるファイルの例:

```
.ts .tsx .js .jsx .py .go .rs .java .rb .php .c .cpp .h
.swift .kt .cs .scala .css .scss .html .vue .svelte
.json .yaml .yml .toml （設定ファイルも含む）
```

**拡張子の一覧は目安であって、判定基準ではない。**ここに無い拡張子でも、
動作を決めているファイルなら同じ扱いにする。

## 直接編集してよい

### 日本語主体のドキュメント

`README.md`、`docs/` 配下、要件定義・設計・タスク分解などの `.md` 成果物。
**文章を書く作業に、コーディングの学習効果はない。**

### 実装コードファイル内の docstring

JSDoc の `/** ... */`、Python の `""" ... """`、その他言語の同等のもの。
日本語主体であれば直接書き込んでよい。**編集範囲を docstring の内側に限定する。**
docstring の外側の処理を巻き込む編集にしない。

書き込むのは **`instructions.md` ステップ3の検証が通ったあと。**提案の段階では含めない。

### フォーマット調整

空白文字数の統一、タブ/スペースの揃え、行末の余分な空白除去など、
**ロジックを一切変えない純粋な見た目の調整。**
全行のインデントを手で直すのは、労力に対して学習効果が低い。

**ただし次は「意味を変える編集」であり、引き続き提案にとどめる:**

- 変数名・関数名のリネーム
- ロジックの変更
- 構文要素の追加・削除

### 読み取り

ファイルの読み込み、ディレクトリ一覧の取得、検索。制限しない。

### 提案文に含めるコード

コードブロックでの提示は「提案」であって「編集」ではない。
擬似コード・サンプルも同様。

## 迷ったときの判定

**「この編集をこちらが代行したら、ユーザーは何を学び損ねるか」**を考える。

答えられないなら代行してよい（フォーマット調整、日本語の文章）。
答えられるなら提案にする（設計判断、制御フロー、命名、型の設計）。
