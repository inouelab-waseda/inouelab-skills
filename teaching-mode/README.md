# teaching-mode

**エージェントにコードを書かせず、提案を受けて自分の手で実装する**ための進め方。

開発を進めながらコーディングスキルを身につけたいときに使う。
「設計は一緒に考える、実装の手は自分が動かす」という分担にする。

## 何が変わるか

| | 通常 | teaching-mode |
|---|---|---|
| コードの入力 | エージェントが書く | **自分で書く** |
| 設計の検討 | エージェントが決めがち | 一緒に考える／意図の説明が付く |
| 完了の判定 | 動けば終わり | **実装として妥当かを検証してもらう** |

## 使い方

呼び出すだけでオンになる。

```text
/teaching-mode
```

タスクを添えれば、そのまま作業に入る。

```text
/teaching-mode ログイン画面のバリデーションを追加したい
```

明示的にオフを伝えるまで続く。セッションをまたいでは持続しない。

## 進み方

```
1. 提案      対象ファイル・編集箇所・コード・設計意図 が提示される
2. 実装      自分で書く。分からないところは質問する
3. 検証      「完了しました」と伝える → 実装として妥当かを見てもらう
             問題なければ docstring がこのタイミングで書き込まれる
4. 質問対応  前後を問わず、なぜそうなるかを聞ける
```

**1タスク = 1チャンク**で進む。複数ファイルの実装がまとめて降ってくることはない。

## 提案どおりに写さなくてよい

**自分で考えた実装を出す方が、学習効果は高い。**検証は「提案と一致しているか」ではなく
**「実装として妥当か」**で行われる。

| 提案と違っていたとき | どう返ってくるか |
|---|---|
| 動作は同じ、書き方が違う | **どちらが良いか比較される。**自分の書き方が良ければ、それが採用される |
| 動作が違う（意図的） | その判断で**何が変わるか**が示される。妥当なら採用される |
| 動作が違う（ミス） | **失敗する入力を1つ挙げて**示される。修正案が返る |

### さらに踏み込む: 先に自分で書く

**「まず自分で書いてみる」と伝えると、提案が出てこなくなる。**代わりに、
何を作るか（入力・出力・満たすべき条件）の合意と、詰まったときのヒントだけが返る。

書けたら「完了しました」で検証に入る。**答えを見る前に考えるので、いちばん効く。**
時間に余裕があるときはこちらを勧める。

## 代行される範囲

手を動かすことに学習効果がないものは、そのまま書き込まれる。

- 日本語主体の `.md`（README、設計ドキュメントなど）
- **docstring**（検証が通ったあと）
- **インデント等のフォーマット調整**（ロジックを変えないもの）

逆に、ロジック・命名・型の設計は必ず提案として返る。
詳しい線引きは [`references/boundaries.md`](references/boundaries.md)。

## 向かないとき

- 実装を代行してほしいとき
- 締切が近く、学習より進行を優先したいとき
- 大量の機械的な修正（一括リネームなど）

そのときはオフにしてよい。**常時オンにするものではない。**
