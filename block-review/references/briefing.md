# 実装計画に含める項目

`instructions.md` のステップ1（実装計画の提示）で使う。**ブロックに着手する前に読む。**

**計画の中心はコードそのもの。**ファイル名や変数名を並べただけでは、レビューできない。
承認する側が判断できる材料を出す。

## 必ず出す

### そのブロックのコード全体

**書こうとしているコードを、そのまま出す。**

- **新規ファイル** — 全体を出す。通常のコードブロックでよい
- **既存編集** — 変更後の関数・領域を**丸ごと**出す。差分の断片だけにしない。
  前後が見えないと、影響が判断できない
- 🔴 **コメントは入れる。**判断の理由や落とし穴を、該当する行の横に書く（次項）
- **docstring は含めない。**実装が確定してから書く（ステップ4）

**これがレビューの対象。**要約や擬似コードで代えない。

### 🔴 コードにはコメントを入れる

**ここで出すコードは、写すものではなくレビューするもの。**
だから、読み手が判断に使う情報は**コードの中に置く。**

`teaching-mode` では逆で、提示したコードはユーザーが手で写す。
コメントは写す量を増やすだけなので本体には入れず、実装後に書き足す。
**block-review はコードを打つのがエージェント側なので、その制約が無い。**

| 書くもの | 例 |
|---|---|
| **判断の理由** | `# 新しい順に見たいので reversed()` |
| **効いている制約** | `# tz 付きで来るので naive に落としてから比較` |
| **落とし穴** | `# ここで return しないと二重に登録される` |

**書かないものの基準は、コードの外の注釈と同じ。**
自明な処理を日本語で言い換えただけのコメントは入れない。

🔴 **コメントに書いたことは、コードの外の注釈から外す。**
同じ説明が2か所にあると計画が長くなり、読み飛ばされる。

**コメントは計画の一部なので、そのまま実装にも入る。**
計画と実装でコメントが変わるのは、承認されたものと違うコードを書いたのと同じ。

### 🔴 既存編集は、変わる行が見える形で出す

**関数を丸ごと出すと、どの行が新しくてどの行が元のままか、読み手には区別できない。**
編集が積み重なるほど区別がつかなくなり、レビューが「全部読み直す」か「読み飛ばす」かの二択になる。

**既存編集は `diff` ブロックで出す。**領域は関数・ブロック単位で丸ごと。その中で——

- 追加する行に `+`、消す行に `-`、変わらない行は先頭に空白
- **変わらない行も省略しない。**文脈として残す（丸ごと出す原則は変わらない）

```diff
 def load_history():
-    data = localStorage.get("history")
+    data = api.get("/api/settlements")
+    if data is None:
+        return []
     return parse(data)
```

**差分の基準は「今ファイルにある状態」。**前のブロックで変えた箇所も、既に書き込まれていれば「元のまま」側に入る。

### 🔴 指摘を受けて計画を直したとき

**直した案は、前回の案との差分だけを出す。**丸ごと出し直さない。

- 変えた箇所を `diff` で。基準は**前回提示した案**
- 変えていない部分は `...` で省き、**「他は前回の案のまま」と1行添える**
- 読み手は前回の案を読んだばかりなので、必要なのは「どこが動いたか」だけ

```diff
 def load_history():
-    data = api.get("/api/settlements")
+    data = api.get("/api/settlements", timeout=5)
     ...
```
> 他は前回の案のまま。

**変更が案の 1/3 を超えるなら、最初の提示と同じ形で丸ごと出し直す。**部分差分では追えない。

### どこに書くか

ファイルパス。新規作成か既存編集か。既存なら、どの関数・どのあたりか。

### 名前の意味

コードに出てくる名前のうち、**意図が読み取りにくいものだけ**1行ずつ添える。
`total` `index` のような自明なものは書かない。

名前は後から変えにくく、読み手が最初に頼る手がかりになる。
**「意図が名前に出ているか」は、レビューする側が指摘できる数少ない点でもある。**

### データの流れ

**何が入り、どう変換され、何が出るか。**
状態を持つなら、**いつ・何をきっかけに変わるか。**

コードを読めば追えることを逐語的に繰り返さない。**追いにくい箇所だけ**書く。

## 判断が生じたときに書く

### なぜこの方針か

🔴 **採らなかった選択肢と、採らなかった理由。**

「A と B があって A にした。理由は X」の形で書く。
**理由が「一般的だから」しか無いなら、判断が生じていないので書かなくてよい。**

### 既存コードへの影響

呼び出し側の変更、型の波及、副作用、削除されるもの。
**このブロックの外に出る影響**を漏らさない。

### 残っているトレードオフ

**どちらでもよい判断が残っているなら、選ばずにユーザーに聞く。**

勝手に決めない。**決めさせることが、いちばん理解に効く。**
選択肢と、それぞれで何が変わるかを示して選んでもらう。

## 書かないもの

- 言語・ライブラリの一般的な解説
- **自明な処理の逐次的な説明**（コードを読めば分かることを、日本語で繰り返さない）
- docstring

**この基準はコメントでも変わらない。**コードの中に入れたからといって、書いてよくなるわけではない。

## 長さの目安

🔴 **コードと注釈を合わせて、画面1つに収まる程度。**

超えるなら、**ブロックが大きすぎる。**分割し直してから出す。
**これがブロックの大きさを決める基準。**行数や関数の個数で切るより、
「1回で読み切ってレビューできるか」で切る。

計画が長いとレビューされずに読み飛ばされ、**承認が形式的になる。
形式的な承認は、乖離を止めない。**
