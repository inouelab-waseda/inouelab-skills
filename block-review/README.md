# block-review

**実装は任せる。ただしブロックごとに実装コードをレビューし、承認してから書かせる。**

AI に実装させたプロジェクトで、**コードは動くが自分では中身を説明できない**——
という状態を防ぐためのモード。手を動かす時間はないが、理解は手放したくないときに使う。

## `teaching-mode` との違い

| | teaching-mode | **block-review** |
|---|---|---|
| コードを見るのは | 実装前 | 実装前（**同じ**） |
| コードを**打つ**のは | **自分** | **エージェント** |
| 理解の担保 | 手を動かすこと | 🔴 **実装前のレビューと、実装後の確認** |
| 向くとき | 学習が主目的。時間がある | **時間がない。でも理解は落としたくない** |

**`teaching-mode` から手書きの部分だけを外したもの。**コードを見てから進む形は変わらない。

## 使い方

```text
/block-review
```

タスクを添えれば、そのままブロック分けから始まる。

```text
/block-review 決済履歴の一覧にページネーションを入れたい
```

## 進み方

```
0. ブロック分け  作業全体を「1回のレビューで読み切れる大きさ」に分割し、一覧で合意する
                 spec駆動でタスク分解済みなら、その単位がそのまま使われる

  ── 以降、ブロックごとに繰り返す ──

1. 計画          🔴 書こうとしているコードがそのまま出る
                 既存コードの編集は diff で（追加行 + / 削除行 -。変わらない行も残る）
                 ＋ どこに書くか / 名前の意味 / データの流れ
                 判断があれば「採らなかった選択肢と理由」も

2. レビュー      承認するまで実装は始まらない。指摘すれば計画が直る
                 直った案は前回との差分だけが出る（他は前回のまま、と明示される）

3. 実装          承認したコードがそのまま書かれる。次のブロックには進まない
                 計画から外れる必要が出たら、その場で止まって報告される

4. 確認          作ったものの一覧 + 計画との差分
                 🔴 そのブロックについての問いが 1〜2 問出る
                 その後 docstring が書き込まれる

  ── 🔴 問いが出たら、そこで止まる ──
     次のブロックの計画は、問いに答えてから出てくる
```

**コードは要約されません。**名前とデータフローだけ渡されても承認しようがないので、
**実際に書かれるコードがそのまま**レビュー対象になります。

**画面1つに収まらないなら、ブロックが大きすぎます。**そこが分割の基準です。

## 🔴 4 の「問い」がこのモードの本体です

計画を読むだけでは、**分かった気になるだけで終わります。**

**固有名詞は問われません。**変数名・関数名・型名は**問いの中に書かれます。**
名前は設計上どちらでもよかった情報で、思い出せるかどうかに意味がなく、
必要になれば検索で取り戻せるからです。

問われるのは、**検索では取り戻せないもの**だけ。

| | 例 |
|---|---|
| **判断の理由** | なぜこの方針にしたか。採らなかった選択肢は何か |
| **変更の影響** | ここを変えたら何が壊れるか |
| **データの流れ** | この値はどこから来て、どこへ行くか |

```
✕  履歴を読み込んでいる関数の名前は？
○  historyStore.load() が localStorage を見ています。
   ここを API に差し替えるとき、呼び出し側で何を変える必要がありますか
```

**答えられなければ、そこが乖離の起点。**その場で埋めてから次のブロックへ進みます。

### 🔴 問いと次の計画は、同じメッセージに来ません

問いが出たら、そのメッセージはそこで終わります。**次のブロックの計画は、答えてから出てきます。**

一緒に出ると、**問いを読み返すために画面を遡る**ことになり、
**「問いへの回答」と「次の計画へのレビュー」を1回の入力にまとめる**必要が生じるためです。

「まとめて進めて」と言った場合も、この規則は変わりません。

### 問いが要らないとき

```text
問いは無しで
```

と伝えれば出なくなります。**作ったものの一覧と、計画との差分は引き続き出ます。**

この場合は問いが無いので、**報告の直後に次のブロックの計画がそのまま続きます。**

## ペースを上げたいとき

**「まとめて進めて」と言えば、ブロックごとに止まらなくなります。**
時間の制約があって使うモードなので、そこは硬直させません。

ただし**コードと確認はブロックごとに出ます。**省けるのは「止まること」だけです。

## 向かないとき

- 何を作るかがまだ決まっていない（先に設計を詰める）
- 使い捨てのスクリプト、理解を残す必要がないもの
- **1ブロックのコードが画面に収まらないほど大きい作業**（ブロック分けからやり直す）
