# block-review

**実装は代行する。ただし、ブロックごとに実装計画を出してレビューを受け、承認されてから書く。**

AI が実装したプロジェクトで、**コードは動くが自分では説明できない**状態を防ぐための進め方。
手を動かす時間はないが、理解は手放したくないときに使う。

自分の手でコードを書きたい場合は `teaching-mode` を使う。**こちらは手書きの部分だけを外したもの**で、
理解を同期させるという目的も、コードを見てから進むという形も変わらない。

## 開始時に伝えること

オンになったことと、**確認の問いを出すこと**を1文で伝える。

```
block-review をオンにしました。ブロックごとに実装計画を出し、承認を得てから実装します。
実装後にそのブロックについて 1〜2 問お聞きします。不要なら「問いは無しで」と言ってください。
```

**「問いは要らない」と言われたらステップ4の問いを出さない。**それ以外はデフォルトで出す。
オフでもステップ4の 1・2（作ったものの一覧、計画との差分）は続ける。

明示的に「オフにして」と言われるまでこのスキルに従う。

## 原則

**理解の同期を、実装の進行より優先する。**

- **レビューを受けていないコードを書かない**
- **承認されていないブロックに着手しない**
- **1ブロックずつ進める。先回りしない**
- 🔴 **1つのメッセージで2つのことを求めない。**問いへの回答と、次の計画のレビューを同時に求めない

## ワークフロー

### 0. ブロックに分ける

作業全体を、**1回のレビューで読み切れる大きさ**に分割する。

- **spec駆動の成果物（タスク分解）があるなら、その単位をそのまま使う。**勝手に切り直さない
- 無ければ分割案を出し、合意を取る
- 目安は「1つの関心事」。1ファイル、または1つの機能単位

**分割の一覧を先に提示して合意を取ってから着手する。**
全体像が無いままブロックを積むと、個々は分かっても全体が分からない状態になる。

### 1. 実装計画の提示

🔴 **そのブロックで書くコードを、そのまま出す。**要約や名前の羅列で代えない。
**コードが無いとレビューできず、承認が形式的になる。**

🔴 **既存コードを編集するブロックは `diff` で出す。**関数・領域は丸ごと出すが、
**追加する行と消す行に印を付ける。**印が無いと、どこが新しいのか読み手に分からない。

🔴 **docstring もコメントも入れて出す。**実装に入るとおりに、最初から書く。
`teaching-mode` と違い、**写す人がいないので写す負担が生じない。**
**あとから足すものを残さない。**実装のときに説明が増えるのは、
承認された内容と違うコードを書いたのと同じ。
コード内に書いたことは、コードの外の注釈からは外す。

コードに添える注釈の項目と `diff` の書き方は、このファイルと同じディレクトリの `references/briefing.md` にある。
**ブロックに着手する前に読む。**記憶で代用しない。

**注釈は簡潔に。**時間が無いから代行しているので、冗長だと読み飛ばされる。
判断の理由は書くが、言語やライブラリの一般的な解説は書かない。

### 2. レビューと承認

**ユーザーのレビューを待つ。明示的な承認があるまで実装に入らない。**

- 質問が来たら答え、**もう一度承認を確認する**
- 指摘が入ったら計画を直し、1 に戻る。**直した案は前回の案との差分だけを出す**（`briefing.md`）。
  丸ごと出し直すと、どこを直したのか読み手が探すことになる
- **無言で先に進まない**

### 3. 実装

**承認されたブロックだけ実装する。次のブロックに進まない。**

**承認されたコードをそのまま書く。**実装中に計画から外れる必要が出たら、
**その場で止めて報告する。**勝手に判断を変えない。**ここが乖離の入口になる。**

### 4. 報告と、理解の確認

実装が終わったら:

1. **何を作ったか** — ファイル・関数の一覧
2. **計画との差分** — あれば明記する。無ければ「計画どおり」と明示する
3. 🔴 **確認の問いを1〜2つ出す**（「問いは無しで」と言われていない場合）

**ここで新しく書き足すものは無い。**docstring もコメントも計画に含まれているので、
実装した時点で揃っている。足りなければ計画が不足していたということ。

### 🔴 問いを出したら、そこでメッセージを終える

**次のブロックの実装計画を、同じメッセージに書かない。**

一緒に出すと、読み手は——

- **問いを読み返すために画面を遡る**ことになる（計画が長いほど問いが埋もれる）
- **「問いへの回答」と「次の計画へのレビュー」を1回の入力にまとめさせられる**

**回答を受け取ってから、次のブロックの計画を出す。**

```
[3/7] 認証ミドルウェア — 完了
（作ったもの・計画との差分）

Q. ...

↑ ここでメッセージを終える。[4/7] の計画は、回答を受けてから出す
```

**「問いは無しで」と言われている場合は、**報告（1・2）の直後に次の計画へ進んでよい。
問いが無ければ、まとめて出しても読み手に二重の負担が生じない。

#### 問いの作り方

**問いは「このブロックを説明できるか」を測るもの。**
計画を読み返せば書いてある、という問いにしない。

🔴 **固有名詞を答えさせない。**変数名・関数名・型名・ファイル名は、**問いの中に書く。**

名前は設計上どちらでもよかった**恣意的な情報**で、思い出せるかどうかに意味がない。
答えられなくても得るものがなく、**問われた側の関心を削ぐ。**
名前は必要になれば検索で取り戻せる。**検索で取り戻せないものだけを問う。**

問うのは次の3つ:

| 種類 | 例 |
|---|---|
| **判断の理由** | なぜこの方針にしたか。採らなかった選択肢は何か |
| **変更の影響** | ここを変えたら何が壊れるか |
| **データの流れ** | この値はどこから来て、どこへ行くか |

```
✕  履歴を読み込んでいる関数の名前は何ですか
○  `historyStore.load()` が localStorage を見ています。
   ここをバックエンドAPIに差し替えるとき、呼び出し側で何を変える必要がありますか
```

答えられなければ、**そこが乖離の起点。**その場で埋めてから次のブロックへ進む。

🔴 **計画を読んで分かった気になるのが、このモードの最大の失敗。**
**理解しているかどうかは、思い出せるかどうかでしか測れない。**

## ペース

**「まとめて進めて」と言われたら従う。**時間の制約があって使われているモードなので、
硬直させない。ただし、まとめた場合も**コードと確認はブロックごとに出す。**
省くのは「1ブロックごとに止まること」であって、レビュー対象そのものではない。

🔴 **まとめた場合も、問いを出したメッセージで終える規則は変わらない。**
問いと次の計画が同じメッセージに入ると、まとめた分だけ遡る距離が長くなる。

## 引き継ぎ

長い作業では、**どのブロックまで終わったか**を都度示す。

```
[3/7] 認証ミドルウェア — 完了
次: [4/7] セッションの保存先
```

ブロックの一覧と進捗が見えていれば、途中で中断しても理解の位置を見失わない。
