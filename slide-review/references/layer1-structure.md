# レイヤー1: 全体の論理構成

スライド**全体**を通した主張の流れを見る。個々のページの中身は見ない（それはレイヤー2）。

このレイヤーの問いは「この順番でページをめくったとき、聴衆の頭の中に意図した理解が組み上がるか」。

**このレイヤーの指摘が最優先。** ここが直っていないと、下のレイヤーをいくら直しても作り直しになる。

以下は**合格条件ではなく、見落としを防ぐための探索リスト**。全て満たす必要はない。話のつながりを良くするものだけを採用する。

---

## 1. ストーリー

研究発表の骨格は次の順になる。

```
背景・目的 → 課題 → 既存研究 → 提案手法 → 実験 → 考察・今後の展望
```

これは既定であって、**実際には個々人の状況に応じて過不足を調整する**もの。機械的に当てはめない。骨格から外れていること自体は指摘にせず、外れた結果として論理がつながらなくなっている場合だけ指摘する。

### 背景・目的

社会的な動機から技術的な問題設定まで、一続きに降ろす節。**社会的意義 → 研究目的 → 入出力関係**の順に具体化していく。

- その研究に取り組むことに**社会的意義**があることが示されているか
- 研究目的が、その社会的課題の解決を目指すものになっているか
- その目的が、**入出力関係**まで具体化されているか（何を入れると何が出てくるのか）
  - 入出力は「背景」ではなく「目的」側の項目。抽象的な目的のままだと、次の「課題」が何の難しさの話なのか読めなくなる
  - 技術的な記述が浮くと感じるなら「課題」の冒頭に置いてもよい。ただし**「課題」より後ろには置けない**

### 課題

- なぜそれが簡単に解決されていないのかが説明されているか
- **一手法の課題ではなく、一般的な課題**として述べられているか
- 課題を自分で作っていないか（自分が設定した状況でしか成り立たない課題になっていないか）

### 既存研究

- その一般的課題に対する解決策を提案している論文が紹介されているか
- 複数のアプローチがある場合、各アプローチの**特徴**が説明されているか
  - ハードウェアを改良するアプローチか、ソフトウェアを改良するアプローチか
  - 深層学習を使うアプローチか、数理モデルを使うアプローチか
- 注目する研究がある場合、その手法が抱えている課題が説明されているか
- 紹介した研究それぞれについて、**なぜそれを採用しないのか**が読み取れるか
- この節が、**提案手法で埋める穴を指し示す形で終わっているか。** ここで穴が示されていないと、次節の貢献の主張が検証できない

### 提案手法

- 既存研究が抱える課題を解決する手法として説明されているか
- **なぜその手法が問題を解決しそうなのか**が説明できているか。「やってみた」で終わっていないか
- 何かを犠牲にした手法である場合、その**トレードオフ関係**に言及しているか
  - 例: 精度が上がることが期待される代わりに、計算時間が増えてしまう

**自分の貢献の範囲が明示されているか。** 貢献は既存研究との差分としてしか定義できないので、前節が示した穴と対応が取れている必要がある。

- この発表で**何が新しいのか**が、はっきり書かれているか
- **既存手法を部品として使う場合、どこまでが借用でどこからが自分の仕事か**が区別できるか
  - 既存手法の適用そのものが貢献になることもあるが、その場合は「別ドメインへの初適用」など、何が新しいのかを言い切る
  - 先行研究が既に同じ組み合わせをやっている場合、それは貢献にならない。差分を別の軸で示す
- 中間発表・進捗報告では、**実装済み / 未実装・検証済み / 未検証**の区別も同じ場所で示されているか

### 実験

- 既存研究の手法と提案手法とを**対照する**実験になっているか
- **客観的な評価指標**が用意され、数字で比較できているか。なぜその指標なのかが説明されているか
- トレードオフがある場合、トレードオフ側の評価もしているか
- **比較条件が揃っているか。** 提案手法以外の差が結果に混ざっていないか
  - データ・計算資源（CPU/GPU）・実装言語・ハイパーパラメータ・実行回数
  - 条件が揃わない場合は、差のどこまでが提案手法由来なのかを述べる
- 比較対象が**何であるか**が、脚注ではなく本文で読み取れるか
- 実験設定が、聞いた人が再現できる程度に書かれているか

### 考察・今後の展望

- 期待通りの結果が出ていない場合、その時点でわかっている範囲の原因が説明されているか
- その時点で自分の手法が抱えている課題に言及し、それを解決するための方向性が示されているか

### 通して読んだときの流れ

- **タイトル（見出し）だけをページ順に読んでいって、話の流れがわかるか**
- 主張が1つに絞られているか。「で、結局何が言いたいのか」に一文で答えられるか
- **「で、何が新しいのか」にも一文で答えられるか。** 貢献が複数ページに散っていて、通しで読まないと拾えない状態になっていないか
- **時系列にこだわっていないか。** 研究に紆余曲折があるのは当然だが、やった順に並べるとストーリーは伝わらない

### スコープは狭める方向にだけ進む

聴衆は、話の対象範囲がだんだん狭くなっていくほうが追いやすい。

```
社会的な文脈 → 分野全体 → 特定の手法 → その手法の中の一部
```

- ページ順に**スコープが単調に狭くなっているか**
- 一度狭めたスコープを、**理由なく広げ直していないか。** 広い話に戻ると、聴衆はそのたびに文脈を組み直すことになる
  - 例: 分野全体の話 → 特定手法の詳細 → また分野全体の話、と往復している
  - 広い話が必要なら、狭める前にまとめて済ませる。ページの順序を入れ替えれば単調にできることが多い
- どうしても戻る場合は、戻ることを明示するか、必要な情報だけ再掲して済ませる
- 例外: まとめ・今後の展望は、意図的に広げ直してよい（狭→広で締める）

**スコープと抽象度は別物。** 具体例を出すことはスコープを広げることではない。抽象度を下げる話はページ内の設計なのでレイヤー2で見る。

### 現在位置がわかるか

ここで見るのは**見出しの列が流れを作るか**。単ページの見出しが中身と合っているかはレイヤー2で見る。

- 各スライドが**何のための**スライドかが、タイトルにハッキリ書かれているか
- **抽象的（マクロ）な見出しと具体的（ミクロ）な見出しを並べる**形になっているか
  - △ `OpenGLとは` — なぜ OpenGL の説明をしているのかが伝わらない
  - ○ `研究背景： OpenGLとは`
- 流れがわからず聴衆が迷子になる箇所がないか

**目次ページは既定では不要。** 論理構成がしっかりしていれば、王道のストーリーに沿っている限り聴衆は次に来るページを予測でき、それ自体が道しるべになる。目次ページの追加は指摘に含めない。現在位置がわからないと感じたら、**まず見出しを直す**。目次は構成の弱さを覆い隠す代償になりやすい。発表が長く、独立性の高い複数テーマを並べる構成の場合だけ検討する。

## 2. 論理の飛躍・欠落

- 前提 → 課題 → 手法 → 結果 → 結論 の連結に飛躍がないか
- 主張を支える根拠（データ・引用・実験結果）が揃っているか。言いっぱなしの主張がないか
- 聴衆が当然抱く疑問に答えるページが欠けていないか

### 専門用語

ここで見るのは**定義の順序**。どの語を選ぶか、一般的な言葉に言い換えられるかはレイヤー2で見る。

- 用語が、**定義される前に使われていないか**
- タイトルに出てくる用語はそれ以前に定義しようがないので、発表中でできるだけ早く説明する
- きちんとした（数学的な）定義が必要かは場合による（理論研究かどうか）
- 分野によって意味が変わる多義語は特に注意

---

## 3. 過不足・配分

- 本筋に寄与しないページがないか
- 持ち時間に対してページ数が妥当か（**目安: 1スライド1分。Appendix は数に入れない**）
- Appendix に回すべき詳細が本編に残っていないか
  - 細かい内容が論理構成上重要なら、本編で説明してよい
  - そうでなければ概要のみ本編に置き、細部は Appendix か論文へ
- 逆に、**本編にあるべき内容が Appendix に落ちていないか**
- 抽象的なページばかりが続いていないか。**具体例で動かして見せるページが、資料全体に1枚もない**状態になっていないか
- 一番言いたいことに一番ページを使えているか。前置きが長すぎないか
- 結論・まとめが尻切れになっていないか
- 以前のスライドの情報が必要になる箇所で、**再掲**されているか
  - 発表中に前のページへ戻るのは避けたい。戻らずに済む構成になっているか

---

## このレイヤーで出す指摘の例

- ページの並べ替え（具体的な順序を示す）
- ページの削除 / Appendix への移動、Appendix から本編への移動
- 不足しているページの追加（何を書くページか明示する）
- セクション分割の変更
- 見出しへのマクロな接頭辞の付与（`研究背景： 〜`）
- 情報を再掲するページの追加
