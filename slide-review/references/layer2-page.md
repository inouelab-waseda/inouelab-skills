# レイヤー2: ページ内構成

**1ページの中**の情報設計を見る。ページの並び順は見ない（それはレイヤー1）。フォント・色・余白・配置も見ない（それはレイヤー3）。

このレイヤーの問いは「このページを数秒見たとき、伝えたい1つのことが伝わるか」。

**大前提**: スライドは聴衆に**見せる**ものであって、書籍・論文のように**読ませる**ものではない。1枚にかけられる時間は限られており、聴衆がそれを読める・聞ける時間も限られている。

以下は**合格条件ではなく、見落としを防ぐための探索リスト**。全て満たす必要はない。項目を満たすことでページの流れが悪くなるなら、その項目は適用しない。

---

## 1. 何をどれだけ載せるか

**原則: 論理構成に必要な要素はすべてスライドに載せる。そのうえで、それ以外は載せない。**
口頭説明はその上に重ねるものであって、必要な要素を口頭に逃がすためのものではない。「なるべくシンプルに」は、この原則を満たしたうえでの話。

- そのページで**言いたいことが1つに絞られているか。** 2つ以上あるならページを分ける
- **そのページの結論が、ページ上のどこかに書かれているか**
  - 見出しが内容と一致しているだけでは足りない。`目的関数の形状` は中身と一致していても、何が言いたいのかは伝わらない
  - 見出しに入れるのが最も効くが、本文の一行でもよい。**形式は問わない**
  - 見出しに入れる場合、現在位置を示すマクロな接頭辞と両立できる。例: `課題： ソートにより目的関数が非平滑になる`
  - 定義や処理フローなど、主張を持たないページに無理に結論を付けさせない
  - 見出しの列が全体の流れを作るかはレイヤー1で見る
- **論理を追うのに必要な要素が、口頭説明に逃がされていないか。** 口頭での補足はほとんど聞き流されると思っておく。スライドだけを見て論理が追えるか
- 逆に、**論理構成に寄与しない要素が載っていないか**
  - 細かい内容が論理構成上重要なら載せてよい
  - そうでなければ概要のみ載せ、細部は Appendix か論文へ
- **全て書き連ねるのではなく、意味単位に分けられているか。** 全て文章で説明しようとしていないか
- **詰め込みすぎていないか。** 目安は**1ページ7〜8行程度**、**1スライド1分程度**で話し切れる量
  - **必要な要素がこの目安を超える場合は、要素を削るのではなくページを分ける。** 目安は詰め込みを止めるためのものであって、必要な要素を落とす根拠にはしない
  - 一覧性とのトレードオフだが、詰め込むよりスカスカのほうがマシ
- 一覧性を上げたい場合、**概略ページ → 個別の具体ページ**の順に分割されているか

## 2. 箇条書き

ここで見るのは**箇条書きの中の並び**。ページ順に話が広がったり狭まったりする話はレイヤー1で見る。

- **同じネストの深さのものが、同じ抽象度の話になっているか**
- **抽象 → 具体の順**になっているか
- 粒度が揃っているか。体言止め / 用言止めが混ざっていないか
- 順番が重要な場合、**番号付きの箇条書き**になっているか
- 無味乾燥な箇条書きが延々と続いていないか
  - ただし、**長々と文章を書くよりは箇条書きのほうが遥かにマシ**。「箇条書きをやめて文章にしろ」という指摘はしない

## 3. 図・表・数式による説明

**図・表・数式は、載せるだけでは何も伝わらない。必ず説明する。** 説明すべきものは2つある。

1. **読み方** — 何が描かれているのか。軸・記号・行と列が何を意味するのか
2. **そこから何が言えるのか** — それがページの主張をどう支えるのか。どこに注目してほしいのか

**ただし、スライドに書くかどうかは文脈で判断する。**

- 前後の流れから役割が自明なものは、読み方をわざわざ書かなくてよい。書くとかえって冗長になる
  - 例: 「結果」の節にある比較表は、見れば結果だとわかる
- **一方、2 は自明になりにくい。** 書かれていなければ指摘する。聴衆は図を読めても、なぜそれを見せられているのかはわからない
- **軸ラベル・単位・凡例・記号の定義だけは、文脈にかかわらず省かない。** これらは説明文ではなく、図・数式そのものの一部

**スライドに書かない場合でも、口頭では必ず説明する。** 文脈で自明として指摘を見送るときは、「スライドには書かなくてよいが、発表では必ず触れること」と添える。省略してよいのは**スライド上の記述**であって、説明そのものではない。

以下は、形式ごとに固有の注意点だけを挙げる。

### 表

- **巨大な表をそのまま貼っていないか。** 発表中に一瞬だけ見せられても、聴衆は何もわからない
- グラフ、または**抜粋した表**で足りないか
- 抜粋できない場合、注目してほしい箇所が**表の中で**示されているか（色・囲みなど）
- 不要なら予備スライドに置き、聞かれたら出す形にできないか

### 図

- その図はページの主張を支えているか。**飾りとして置かれていないか**
- 引用図に**出典**があるか（研究倫理上、これは省略しない）
- **図・表番号は基本的に付けなくてよい。** 論文・レポートのようにカッチリさせる必要はない
  - 番号があること自体は指摘しなくてよい。ただし「図1で……」と後から参照する構成になっている場合は指摘する。聴衆は覚えていない
- ページ全体が図の説明である場合、図にタイトルを付けるのではなく、**スライドのタイトルに図のタイトルを書く**
- 図へのコメントは、吹き出しなどで**その図の上に直接**書かれているか

### 数式・定義と抽象度

**抽象的な説明だけで終わっていないか。** 抽象的な話だけで進むと、聴衆はすぐに置いていかれる。抽象度を下げるのは、原則として**そのページの中**でやる。

- その数式・定義の**「意味」が自分の言葉で**書かれているか。読み上げるだけでは伝わらない
  - 例: `y'' = -9.8` → △「鉛直方向の加速度を -9.8 とする」／◎「重力加速度として、鉛直方向に -9.8 の加速度を与える」
- **同じページの中で**、定義の前後に**モチベーションと例**が添えられているか
  - なぜその定義が出てくるのか（前）／具体的にどう使うのか（後）
  - 例のページを別に足す話はレイヤー1で見る
- 英語を読むより数式を読むほうが難しいことは多い。読み手の負荷を低く見積もらない

### アルゴリズム・関数・手続き

- 長々と文章で書いていないか。**番号付き箇条書き**か**擬似コード**で説明されているか
- **フローチャート**など図で描かれているとさらに良い。あるいは具体的な入力例を1段階ずつ実行して見せる
- フローチャートは丁寧に描かれているか。**「パッと見で、だいたい分かる」が大事**で、「よく見ればしっかり分かる」ではダメ

## 4. 言葉づかい

ここで見るのは**語の選択と文**。用語が定義される前に使われていないかという順序の問題はレイヤー1で見る。

- **誰を対象としているかを踏まえた言葉になっているか**
- **専門用語をなるべく避け、一般的な用語で説明できないか**
- **定義があいまいなまま使われている用語がないか。** 指す範囲が読み手によって変わる語を、断りなく使っていないか
- 同じものが**同じ呼称で**呼ばれているか。ページをまたいで呼び方が変わっていないか
- **主語と述語が食い違っていないか**
  - ✗「この関数は、……という手法である。」
  - 括弧などを跨いだ際は、特に前後が正しく繋がっているか確認する
- **一文一義**になっているか。文が長くなると不整合が起きやすい
- **読点が適量使われているか。** 句読点なしで1行以上に及んでいたら、何かがおかしい
- 文の途中で改行していないか
  - どうしても2行にわたる場合、**単語をぶった切らない**。切りの良いところで思い切って改行する
- 長文を載せる場合、**大事なところ・キーワードが強調**されているか

## このレイヤーで出す指摘の例

- 見出しの書き換え案（結論型に）
- ページの分割 / 統合
- 箇条書きのネスト・順序の組み替え
- 表 → グラフ、表 → 抜粋、文章 → 擬似コード / フローチャート
- 図表・数式への説明の追記、数式への解釈・モチベーション・例の追加
- 専門用語のより一般的な言い換え、呼称の統一
- 具体的な文言の書き換え案（係り受け・文の分割・改行位置）
