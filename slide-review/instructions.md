# slide-review

発表スライドを**3つのレイヤー**で順にレビューする。各レイヤーの詳細な観点は、このファイルと同じディレクトリの `references/` に置かれている。**そのレイヤーをレビューする直前に、対応するファイルを必ず読むこと。** 記憶で代用しない。

| レイヤー | 見るもの | 詳細 |
|---|---|---|
| 1. 全体の論理構成 | スライド全体を通した主張の流れ | `references/layer1-structure.md` |
| 2. ページ内構成 | 1ページの中の情報設計 | `references/layer2-page.md` |
| 3. デザイン | 視覚表現・体裁 | `references/layer3-design.md` |

対象は**日本語の研究発表スライド**（ゼミ・中間発表・学会発表など）。観点もそれを前提に書かれている。英語のスライドは対象外。依頼されたら、日本語前提の観点（約物・係り受け・和文フォントなど）が適用できないことを伝えたうえで、レイヤー1を中心に見る。

発表者の所作・準備プロセス（原稿を読まない、練習、リハーサル、話し方など）は**レビュー対象外**。気づいても指摘しない。

## 実行手順

### 0. 入力の取り込み

対象スライドを受け取る。形式ごとの扱い:

- **Marp / Slidev / reveal.js など Markdown ベース** — ソースをそのまま読む。これが最も精度が高い。
- **PDF** — 各ページを画像として見る。ページ数が多い場合は分割して読む。レイヤー3はここでしか判定できないので、必ず目で見る。
- **PowerPoint / Keynote** — PDF に書き出してもらう。テキスト抽出だけだとレイヤー3が評価できない。
- **画像** — そのまま見る。

利用中の環境が画像や PDF を読めない場合は、その旨を伝えたうえでレイヤー1・2 のみ実施する。見ていないものについて推測で指摘しない。

ページ番号は最後まで一貫して使うので、最初に**総ページ数と各ページの見出し一覧**を作ってから始める。

### 0.5. 前提の確認

以下が未知でレビュー結果が変わる場合のみ、まとめて1回だけ聞く。推測できるなら聞かずに進め、置いた前提を明記する。

- 発表の場（ゼミ / 学会 / 中間発表 / 対外発表）
- 持ち時間
- 聴衆の前提知識（専門が近いか、初見か）
- 発表資料か、読み物として配布されるか

### 1〜3. 各レイヤーのレビュー

**必ずレイヤー1 → 2 → 3 の順で行う。** 上位レイヤーの指摘が下位を無効化するため。構成ごと消えるページのフォントサイズを指摘しても意味がない。

各レイヤーで:

1. 対応する `references/` のファイルを読む
2. そこに書かれた観点で全ページを通す
3. 指摘を出す

レイヤーが指定された場合（`structure` / `page` / `design`、または `1` / `2` / `3`）は、そのレイヤーのみ実行する。指定がなければ全レイヤーを実行する。

### 下位レイヤーの指摘が無駄になる場合

レイヤー1で**削除・移動・分割・統合**を提案したページについては、そのページに対するレイヤー2・3の指摘を通常どおり並べない。`保留` としてまとめ、件数だけ示す。

```
### 保留（レイヤー1の対応後に再確認）
- p.8-11 — 統合を提案しているため、確定後に見直す（ページ内構成 2件 / デザイン 1件）
```

消えるかもしれないページの文言や配色を先に直させない。

## 評価の原則

**`references/` の各項目は合格条件ではない。** 見落としを防ぐための探索リストであって、全項目を満たす必要はないし、満たすこと自体を目標にしない。デザインに100点満点の答えはなく、良し悪しを判断するのは人間の主観。目指すのは60〜80点で、それ以上は時間対効果が割に合わない。

**チェックリストの充足度をレビュー結果にしない。** 点数も付けない。

次の3つは、個々の観点より上位に立つ。観点とぶつかったら、こちらが勝つ。

1. **接続性が最優先。** ある観点を満たすことで前後のページとのつながりが悪くなるなら、**その観点は適用しない。** 指摘を出さないか、どうしても触れるならトレードオフとして一言添えるにとどめる。個別の観点を満たした結果スライドとして読めなくなるなら、レビューとして失敗している。
2. **帰結を言えない指摘は出さない。** 「観点Xに反している」は理由にならない。**どのページで、聴衆が具体的にどう詰まるか**を言えるものだけを指摘する。言えないなら `nits` に落とすか、そもそも書かない。
3. **単ページ最適化をしない。** レイヤー2・3の修正案は、レイヤー1の流れを壊さないか確認してから出す。壊すなら出さない。

### 件数

- `must` に上限は設けない。直さないと伝わらないものは、何件でも挙げる
  - ただし絞り込みは上の 2 で行う。**帰結を言えないものは `must` にしない**
- `should` は最大7件
- `nits` は件数のみ示し、詳細は求められたら出す

観点を網羅した長いリストより、直せば確実に良くなる数件のほうが資料は良くなる。`should` と `nits` を削って `must` を通す。

## 指摘の出し方

- **ページ番号を必ず添える。** 「p.7 の図が〜」の形。レイヤー1のように全体にかかる指摘は `全体` と書く。
- **重要度を付ける。** `must`（直さないと伝わらない） / `should`（直すと良くなる） / `nits`（好みの範囲）。`must` から並べる。
- **代案を出す。** 「わかりにくい」で止めない。どう直すかまで書く。ページの入れ替えなら具体的な順序、文言なら書き換え案。
- **良い箇所も1〜2点挙げる。** 壊してほしくない部分を守るため。

### レイヤーをまたぐときの優先順位

**レイヤー番号の小さいほうを常に優先する。** 修正コストが 1 > 2 > 3 の順に大きく、かつ上位の修正は下位の修正を作り直させるため。レイヤー1の `should` は、レイヤー2の `must` より先に着手させる。

順位付けのキーは次の順:

1. **レイヤー番号**（1 → 2 → 3）
2. **重要度**（`must` → `should`）
3. 影響するページ数の多いもの

ただし `nits` はレイヤーを問わず最後。レイヤー1の `nits` がレイヤー3の `must` より先に来ることはない。

レイヤー1に `must` が残っている間は、レイヤー3の詳細を長々と並べない。件数と代表例だけ示し、「レイヤー1の対応後にもう一度かけてほしい」と伝える。

## 出力フォーマット

```
## 前提
（確認 or 仮置きした前提。持ち時間・聴衆など）

## レイヤー1: 全体の論理構成
### must
- [全体] ...
### should
- [p.3-5] ...

## レイヤー2: ページ内構成
（同上）

## レイヤー3: デザイン
（同上）

### 保留（レイヤー1の対応後に再確認）
- ...

## 良い点
- ...

## 次にやること
1. ...
2. ...
3. ...
```

最後の「次にやること」は**着手順**。前掲の優先順位（レイヤー番号 → 重要度 → 影響範囲）で上から3つを選ぶ。ここだけ読めば動けるようにする。

各項目には出どころのレイヤーを添える（`[L1]` `[L2]` `[L3]`）。レイヤー1の項目が残っているうちは、そこで一度手を止めて再レビューに出すよう促す一文を添える。
